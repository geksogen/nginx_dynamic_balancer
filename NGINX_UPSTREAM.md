# ⚖️ `upstream` в Nginx

Блок `upstream` в Nginx — это мощный инструмент для управления кластерами серверов (бэкендами). Он определяет, куда и по каким правилам Nginx будет проксировать входящий трафик.

В этом документе собраны основные директивы и параметры, которые позволяют гибко настроить балансировку нагрузки, отказоустойчивость и кэширование соединений.

---

## 🚦 1. Алгоритмы балансировки (Как распределять трафик)

Если алгоритм не указан явно, Nginx использует **Round Robin** (распределение запросов по очереди к каждому серверу). Для изменения логики используйте следующие директивы:

| Директива | Описание и применение |
| :--- | :--- |
| **`least_conn;`** | Направляет запрос на сервер с **наименьшим количеством активных соединений**. Идеально для тяжелых запросов, время обработки которых сильно варьируется (например, генерация отчетов или скачивание файлов). |
| **`ip_hash;`** | Маршрутизирует запросы на основе IP-адреса клиента. Гарантирует, что конкретный пользователь **всегда будет попадать на один и тот же сервер** (пока тот доступен). Полезно для "липких сессий" (sticky sessions). |
| **`hash <ключ> [consistent];`** | Распределяет трафик на основе любой переменной (например, `$request_uri` или `$remote_addr`). Флаг `consistent` включает консистентное хеширование. Отлично подходит для пула кэширующих серверов. |
| **`random [two [method]];`** | Направляет запрос на **случайный сервер**. При параметре `two` Nginx выбирает два случайных сервера, а затем применяет к ним метод (по умолчанию `least_conn`), чтобы выбрать лучший. |

---

## ⚙️ 2. Параметры серверов (Управление конкретными узлами)

Эти параметры указываются в строке с директивой `server` и позволяют настраивать веса и пассивные проверки доступности (Health Checks).

| Параметр | Пример | Описание |
| :--- | :--- | :--- |
| **`weight=N`** | `server 10.0.0.1 weight=3;` | Устанавливает "вес" сервера (по умолчанию 1). В данном примере сервер получит в 3 раза больше запросов, чем стандартный. |
| **`max_fails=N`** | `server 10.0.0.1 max_fails=3;` | Количество неудачных попыток связи (ошибки, таймауты), после которых сервер считается "упавшим". (0 отключает проверку). |
| **`fail_timeout=T`**| `server 10.0.0.1 fail_timeout=30s;`| Время, на которое сервер выводится из ротации после достижения лимита `max_fails`. |
| **`backup`** | `server 10.0.0.2 backup;` | Резервный сервер. Трафик пойдет на него **только** если все основные серверы недоступны. (Несовместим с `ip_hash` и `hash`). |
| **`down`** | `server 10.0.0.3 down;` | Искусственно выводит сервер из ротации. Удобно для безопасного проведения технических работ на узле. |
| **`max_conns=N`** | `server 10.0.0.4 max_conns=100;` | Защита от перегрузки: ограничивает максимальное количество одновременных активных соединений к этому бэкенду. |

## 🔌 3. Управление состояниями и соединениями

Эти директивы настраиваются внутри блока `upstream` и влияют на производительность и обмен данными между рабочими процессами (workers) Nginx.

* **`zone <название> <размер>;`**
  Создает зону в разделяемой памяти (Shared Memory). Обязательна для того, чтобы все worker-процессы Nginx синхронизировали между собой статистику падений (`max_fails`) и текущее состояние бэкендов.
  *Пример:* `zone backend_zone 64k;`

* **`keepalive <число>;`**
  Кэширует указанное количество простаивающих (keepalive) TCP-соединений с бэкендами. Критически важно для снижения задержек, так как избавляет от необходимости делать TCP-хендшейк на каждый новый запрос.
  *Пример:* `keepalive 32;`

* **`keepalive_requests <число>;`**
  Максимальное количество запросов, которые можно отправить через одно открытое keepalive-соединение перед его принудительным закрытием.

* **`keepalive_timeout <время>;`**
  Время, в течение которого неактивное соединение с бэкендом будет удерживаться открытым в пуле.

## 🏗️ 4. Полный пример конфигурации (Best Practices)

В этом примере собраны лучшие практики для настройки надежного и быстрого кластера.

```nginx
upstream backend_cluster {
    # 1. Выделяем общую память для синхронизации статуса серверов между воркерами Nginx
    zone backend_zone 64k;

    # 2. Выбираем алгоритм: отдаем приоритет серверам с наименьшей нагрузкой
    least_conn;

    # 3. Основной пул серверов
    # Мощный сервер, берет на себя двойную нагрузку
    server 192.168.1.10:8080 weight=2 max_fails=3 fail_timeout=15s;
    # Стандартный сервер
    server 192.168.1.11:8080 max_fails=3 fail_timeout=15s;

    # 4. Обслуживание и резервирование
    # Сервер временно выведен на техобслуживание
    server 192.168.1.12:8080 down;
    # Включится только если .10 и .11 перестанут отвечать
    server 192.168.1.20:8080 backup;

    # 5. Оптимизация сети: держим пул из 16 открытых соединений
    keepalive 16;
}

server {
    listen 80;
    server_name api.example.com;
    
    location / {
        proxy_pass http://backend_cluster;
        
        # Обязательные заголовки для корректной работы keepalive к бэкенду
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        
        # Передаем реальные IP клиентов
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
